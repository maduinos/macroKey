# macroKey 아키텍처

버튼 8개짜리 Pro Micro 키패드를 "고정 단축키 8개"에서 "확장 가능한 매크로 플랫폼"으로
바꾸기 위한 설계 문서입니다. 하드웨어 배선은 [`HARDWARE.md`](HARDWARE.md), 호스트와 장치가
주고받는 문자열 규격은 [`PROTOCOL.md`](PROTOCOL.md)에 따로 정리했습니다.

## 1. 설계 원칙

1. **Device-first, host-optional** — 펌웨어만 올려도 평범한 USB HID 키보드/마우스로 동작합니다.
   호스트 앱은 없어도 되는 증폭기이지 필수 런타임이 아닙니다. PC를 바꿔도, 앱을 안 깔아도
   키패드는 기본 기능을 합니다.
2. **정책과 메커니즘 분리** — 펌웨어는 "무엇을 눌렀나"를 이벤트로 만들고, "무엇을 할까"는
   프로필 테이블이 정합니다. 새 매크로를 추가할 때 펌웨어를 다시 빌드하지 않습니다.
3. **확장은 코드 수정이 아니라 등록으로** — 액션 타입은 테이블 항목 추가, 호스트 액션은
   registry 등록, LED 효과는 함수 포인터 추가로 늘어납니다. `if` 사슬을 늘리지 않습니다.
4. **모든 경계에 버전을 박는다** — 시리얼 프로토콜, EEPROM 프로필, 호스트 설정 JSON 각각
   독립 버전을 갖고, 상위 버전을 만나면 조용히 오동작하는 대신 거부하거나 마이그레이션합니다.
5. **설정 앱은 런타임이 아니다** — 패드는 HID로 혼자 동작하고, PC 앱은 프로필
   편집·녹음·동기화만 합니다.

## 2. 계층 구조

```
┌──────────────────────────────────────────────────────────────┐
┌──────────────────────────────────────────────────────────────┐
│ L4  설정 앱 (Python, macrokey 패키지) — 설정 시에만            │
│     profile store │ recorder │ push/pull                      │
└───────────────────────────┬──────────────────────────────────┘
                            │ USB CDC 시리얼, protocol v1 (PROTOCOL.md)
┌───────────────────────────▼──────────────────────────────────┐
│ L3  펌웨어 코어                                               │
│     KeyEngine · ProfileStore(EEPROM) · LedController          │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ L2  HAL   ButtonInput(핀) · HidBackend(HID) · Storage(EEPROM) │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ L1  하드웨어   버튼 8 · WS2812B 1 · 보드 native USB            │
└──────────────────────────────────────────────────────────────┘
```

각 계층은 아래 계층만 압니다. `KeyEngine`은 시리얼을 모르고, `LedController`는 버튼을 모르며,
호스트 앱은 어떤 핀에 무엇이 붙었는지 모릅니다.

### 2.1 보드 축

계층과 직교하는 축이 하나 더 있습니다. **어떤 보드인가**입니다. 보드가 바뀌면 달라지는 것은
핀, 저장소의 크기와 종류, 이름, 부트로더 넷뿐이고 나머지는 전부 같습니다. 그 넷은 양쪽에서
각각 한 곳에 모여 있습니다.

| | 한 곳 | 그로부터 파생되는 것 |
| --- | --- | --- |
| 펌웨어 | `firmware/src/boards/<board>.h` | 핀·EEPROM 크기·카운트 폭·스키마·슬롯 상한·부트로더 진입. `boards/board.h`가 고르고, 빠진 심볼을 `#error`로 잡습니다 |
| 호스트 | `macrokey/boards.py` | 프로필 레이아웃(`config/binary.py`), USB 인식(`device/discovery.py`), 펌웨어 이미지와 플래싱 방법(`flash/`), 그리고 테스트 |

`boards/` 바깥의 펌웨어 코드는 아키텍처 매크로를 직접 보지 않습니다. 호스트 쪽에서 보드를
나열하는 곳도 `boards.py` 하나뿐입니다. 새 보드는 [BOARDS.md](BOARDS.md)의 체크리스트대로
파일 셋(레지스트리·헤더·문서)을 더하면 되고, 하나라도 빠지면 테스트가 실패합니다.

## 3. 8개 버튼을 96개 슬롯으로 — 입력 모델

물리 키가 8개뿐이라는 제약을 **제스처**로 넘습니다.

### 3.1 제스처

`ButtonInput`이 원시 핀 상태를 다음 이벤트로 정규화합니다.

| 제스처 | 발화 시점 | 용도 |
| --- | --- | --- |
| `TAP` | 짧게 눌렀다 뗐을 때 | 기본 단축키 |
| `DOUBLE` | 임계 시간(기본 250 ms) 안에 두 번 탭 | 파괴적/드문 동작 |
| `HOLD` | 임계 시간(기본 400 ms) 넘게 유지 | 바인딩 불가 — 녹음 진입점 |

`HOLD`는 400 ms에 한 번 보고되지만 바인딩할 수 없습니다. 3초 단독 홀드가 녹음이라서,
그 외에는 임계 시간에 한 번 발화합니다. 하나의 슬롯이 두 의미를 겸하므로
제스처 종류를 늘리지 않고도 modifier 키패드처럼 쓸 수 있습니다.

`TAP`과 `DOUBLE`의 충돌은 흔한 함정입니다. 해당 키의 `DOUBLE` 슬롯이 비어 있으면 `TAP`을
릴리스 즉시 내보내고, 채워져 있을 때만 double 임계 시간만큼 지연시킵니다. 즉 **비용은 그
기능을 실제로 쓰는 키만 냅니다.**

### 3.2 슬롯

키 8개 × 바인딩 가능한 제스처 2개 = **16 슬롯**.

레이어는 제거되었습니다. 보이지 않는 모드와 외워야 하는 진입 방법을 만들었고, 그 대가로
키맵 EEPROM을 먹었습니다. 남은 것은 거의 모든 호출에 붙어 다니며 언제나 0이던 `layer`
인자뿐이었고, 그것도 함께 없앴습니다. 그 바이트는 매크로 레코드가 씁니다.

### 3.3 hold — 녹음 진입점

hold는 바인딩할 수 있는 제스처가 **아닙니다.** 키 하나를 단독으로 3초 누르면 장치가
`EV t=record`를 보내고, 그것이 녹음의 시작이자 종료입니다. "단독"이 조건인 이유는 다른
키를 같이 누른 채 홀드하는 건 패드를 *쓰는* 동작이지 *프로그래밍하는* 동작이 아니기
때문입니다.

400 ms 지점에서 `g=hold`가 한 번 보고되므로, hold에 뭔가 바인딩되어 있으면 한 번의 누름이
서로 무관한 두 가지를 일으킵니다. 그래서 `Profile.set_action`이 hold 바인딩을 아예
거부하고, 키맵에도 자리를 두지 않습니다.

**어느 슬롯에 녹음할지도 홀드가 정합니다.** 그냥 홀드하면 tap, 더블클릭 후 홀드하면
double입니다. 이 판정은 릴리즈→프레스 간격만 보며, 탭 지연 마스크(`doubleTapMask_`)와
분리되어 있습니다. 그 마스크는 *이미 더블 바인딩이 있는 키*에만 켜지는데 녹음이 필요한
건 정확히 비어 있는 키라서, 그것에 얹었으면 닭과 달걀이 됩니다.

코드(chord)는 제거되었습니다. 편집 수단이 없어 채울 방법이 없는 40바이트였고, 지금은
매크로 레코드가 씁니다.

## 4. 액션 모델 — 무엇을 어디서 실행하는가

액션은 **장치에서 끝나는 것**과 **호스트가 받아 처리하는 것**으로 나뉩니다. 이 분리가
이 설계의 핵심입니다.

| ID | 액션 | 실행 위치 | 페이로드(3바이트) |
| --- | --- | --- | --- |
| 0 | `NONE` | — | — |
| 1 | `KEY` | 장치 | modifiers, keycode, 플래그(sticky) |
| 2 | `CONSUMER` | 장치 | usage 하위/상위 바이트 (볼륨·재생·밝기) |
| 3 | `MOUSE_BUTTON` | 장치 | 버튼 마스크, 모드 (0 클릭 / 1 누름 / 2 뗌) |
| 4 | `MOUSE_MOVE` | 장치 | dx, dy (int8), 스텝 |
| 5 | `MOUSE_WHEEL` | 장치 | delta (int8) |
| 6, 7 | *(퇴역)* | — | 레이어 전환이었습니다. 번호는 재사용하지 않습니다 |
| 8 | `SEQUENCE` | 장치 | 장치 매크로 테이블 인덱스 |
| 9 | *(퇴역)* | — | 예전 `HOST` 토큰. 번호는 재사용하지 않습니다 |
| 10 | `LED_SCENE` | 장치 | 없음. 프로필 씬으로 되돌립니다(픽셀당 팔레트가 하나뿐이라 고를 씬이 없습니다) |
| 11 | `DELAY` | 장치 | 10 ms 단위 지연 (매크로 레코드 전용) |
| 12 | `TEXT` | 장치 | 문자 수. 문자는 뒤따르는 레코드에 3개씩 (매크로 전용) |

`MOUSE_BUTTON`의 모드가 0/1/2인 이유는 **드래그** 때문입니다. 누름과 뗌을 항상 한 번의
클릭으로 합치면 드래그 앤 드롭이 "클릭 → 순간이동 → 클릭"으로 재생됩니다. 매크로가
중간에 끊겨도 버튼이 눌린 채 남지 않도록, 재생이 끝나면 펌웨어가 모든 버튼과 키를
무조건 놓습니다.

`TEXT`는 4바이트 키맵 슬롯에 들어갈 수 없습니다(레코드 여러 개를 차지하므로). 매크로
안에서만 쓰이고, 이것이 녹음 용량을 세 배로 만든 변경입니다.

**장치 액션**은 EEPROM만 있으면 되므로 앱 없이 동작하고 지연이 1 ms 미만입니다.
단축키, 볼륨, 마우스 클릭처럼 자주 쓰는 것들이 여기 들어갑니다.

**호스트 액션은 없습니다.** 예전 `HOST` 토큰(id 9)은 퇴역했고, PC 앱은 설정·녹음만 합니다.
설정이 끝나면 앱을 꺼도 패드는 HID로 동작합니다.

## 5. 메모리 예산 — 왜 이 형태인가

ATmega32u4는 SRAM 2.5 KB, EEPROM 1 KB입니다. 이 두 숫자가 자료구조를 결정했습니다.

**액션은 4바이트 고정**(`type`, `a`, `b`, `c`)입니다. 가변 길이로 만들면 파서가 커지고
EEPROM 조각화가 생깁니다.

EEPROM 배치:

EEPROM 배치 (schema 2):

| 영역 | 크기 | 내용 |
| --- | --- | --- |
| 헤더 | 16 B | magic, schema version, 밝기, 플래그, CRC16 |
| 키맵 | 64 B | 8 키 × **2 제스처** × 4 B |
| LED 팔레트 | 3 B | 1 픽셀 × RGB (쉬는 색) |
| 매크로 인덱스 | 16 B | 슬롯당 레코드 수 1 B |
| 매크로 레코드 | 925 B | **308개** × 3 B |
| 합계 | 1024 B | EEPROM 전부 |

**남는 바이트를 두지 않습니다.** 매크로 영역 크기는 손으로 적는 대신 `MK_EEPROM_SIZE -
MK_MACRO_OFFSET`으로 유도합니다. 480 → 768로 두 번 손으로 늘렸고 두 번 다 바이트를
남겼습니다.

세 가지가 녹음 용량을 위해 회수되었습니다:

- **제스처 2개만 저장.** hold는 녹음을 여는 방법이라 아무것도 바인딩할 수 없고, 그 칸은
  모든 키에서 0으로만 채워져 있었습니다. 32 B.
- **코드(chord) 영역 삭제.** 에디터가 편집 수단을 준 적이 없고 기본값도 비어 있어서, 8개
  슬롯 전부가 영구히 0이었습니다. 40 B.
- **인덱스에서 오프셋 제거.** 슬롯은 순서대로 채워지므로 시작 위치는 앞 슬롯들의 레코드
  수 합입니다(`Profile::macroBase`). 32 B — 그리고 인덱스와 영역이 매크로 시작점을 두고
  서로 다른 말을 하는 종류의 버그가 통째로 사라집니다.

**레코드는 스텝이 아닙니다.** 타이핑한 텍스트는 헤더 레코드 1개 + 문자 3개당 1개입니다.
이전에는 문자마다 3바이트짜리 KEY 액션이었고, 그래서 `sudo apt update && sudo apt upgrade
-y` 한 줄이 38 스텝(전체 273개 중)이었습니다. 지금은 14 레코드입니다. 텍스트 기준 실질
용량은 약 273자 → 약 900자입니다.

팔레트는 `MK_LED_COUNT`에서 자동으로 따라옵니다. 픽셀을 늘리면 그만큼 매크로 영역이
줄어들 뿐, 합계는 언제나 1024 B입니다.

RP2040 빌드는 AVR 배치를 변경하지 않고 별도 schema 3을 씁니다. 16 MB 플래시 중
14 MB를 LittleFS로 예약하고, 고정 65,520 B 프로필(2 B 슬롯 카운트, 총 21,801
레코드)을 임시 파일에 쓴 뒤 이름을 바꾸어 커밋합니다. 이 크기는 264 KB SRAM에
라이브 이미지와 전송 스테이징 이미지를 동시에 둔 채 원자적 갱신을 유지하는 상한입니다.

**키맵을 RAM에 미러링하지 않습니다.** 키를 누른 순간 EEPROM에서 4바이트를 직접 읽습니다.
AVR EEPROM 읽기는 바이트당 약 4 사이클이라 사람 손가락 기준으로는 즉시나 마찬가지고,
이 결정 하나로 SRAM 384바이트를 아낍니다. 절약한 SRAM은 LED 프레임 버퍼(1 × 3 B)와
시리얼 라인 버퍼(96 B)가 씁니다.

## 6. LED 파이프라인

WS2812B 1개는 **피드백 장치**입니다. 소스를 우선순위로 합성합니다.

```
우선순위 높음
  1. 키/매크로 큐        탭 흰색 · 빈 슬롯 어두운 빨강 · 매크로 완료 초록
  2. 매크로 실행 중      시안 펄스 (시퀀스 재생 동안)
  3. 호스트 오버레이     녹음 중 빨강/분홍 등 (설정 앱이 잠깐 host 모드)
  4. 기본 씬            프로필 팔레트
우선순위 낮음
```

픽셀이 하나라 키별 위치 표시는 없고, 어느 키든 같은 픽셀이 반짝입니다.
AgentPet 상시 앰비언트는 제거되었습니다(설정 앱이 상시 실행되지 않음).

### 6.1 소유권과 워치독

설정·녹음 중에만 앱이 `LED mode=host`로 오버레이를 잡습니다. 타임아웃이 지나면 장치가
로컬 씬으로 돌아갑니다.

### 6.2 전력 상한

픽셀 1개는 흰색 최대에서 약 60 mA입니다. MCU 30 mA를 더해도 90 mA로 USB 500 mA 예산의
18%밖에 안 쓰므로 전력은 실질적인 제약이 아닙니다. 그래도 `LedController`는 프레임을
내보내기 전에 채널 합을 계산해 `MK_LED_MAX_MILLIAMPS`(현재 100 mA)로 스케일 다운합니다.
이 코드를 남겨 둔 이유는 `MK_LED_COUNT`를 올리는 순간 다른 곳을 고치지 않아도 바로
안전장치가 되기 때문입니다. 자세한 계산은 [`HARDWARE.md`](HARDWARE.md#전력-예산)에 있습니다.

## 7. 매크로 레코딩 — "동작을 로깅해서 키에 할당"

호스트 앱의 recorder가 실제 입력을 잡아 액션 시퀀스로 바꿉니다.

```
캡처            정규화              편집             할당
evdev/pynput 리스너 → RawEvent 스트림 → 정규화된 스텝 → 슬롯(키·제스처)
```

정규화 단계에서 하는 일:

- **modifier 접기** — `ctrl↓ c↓ c↑ ctrl↑` 를 `hotkey ctrl+c` 하나로 합칩니다.
- **지연 양자화** — 사람의 들쭉날쭉한 간격을 10 ms 단위로 반올림하고, 임계값(기본 40 ms)
  미만은 버립니다. 그대로 재생하면 사람 타이핑 속도로 느리게 재생됩니다.
- **연속 문자 병합** — 낱개 키 입력을 `text` 액션 한 개로 묶습니다. 15자 문자열이
  30개 이벤트가 되는 것을 막습니다.
- **자기 입력 제외** — 레코딩 중 매크로 키패드 자신이 보낸 입력은 무시합니다. 아니면
  녹화가 자기 자신을 잡아먹습니다.
- **마우스 시간 보존** — 수백 Hz의 raw 이동을 50 ms 조각으로 합칩니다. 전체 드래그를 한
  순간의 큰 HID 이동으로 바꾸면 OS 포인터 가속이 달라져 도착점이 어긋나기 때문입니다.
  **그 시간을 실제로 쓰는 쪽은 펌웨어입니다** — 아래 7.1 참고.
- **명시적 좌표 의미** — 기본은 현재 포인터 기준 상대 재생입니다. 같은 화면 위치가 필요한
  경우에만 녹음·재생 양쪽에 `mouse_home`을 넣는 실험적 고정 위치 모드를 사용합니다.

정규화된 결과가 장치 액션 하나면 EEPROM에, 시퀀스면 매크로 슬롯에 저장합니다.
장치가 재생할 수 없으면 **거절**하고 기존 바인딩은 그대로 둡니다(호스트 fallback 없음).
거절 사유는 막은 스텝을 지목합니다 — "짧게 만들라"는 안내는 실제로 길이가 문제일 때만
나옵니다.

### 7.1 재생 속도 — 왜 이동을 한 번에 쏘지 않는가

패드는 **상대 좌표** 마우스입니다. "이만큼 움직여라"를 보내면 화면에서 얼마나 가는지는
데스크톱이 정합니다. 그리고 적응형 포인터 가속은 그 판단을 **델타가 얼마나 빨리
들어오는지**에 따라 바꿉니다.

한 레코드는 50 ms짜리 이동 *조각*이지 점프가 아닙니다. 실제 마우스는 그 50 ms 동안
2 counts짜리 리포트를 50번쯤 보냈는데, 이것을 100 counts 리포트 하나로 재생하면 가속
곡선은 그것을 "매우 빠른 움직임"으로 읽고 증폭합니다. 매크로는 오버슈트하고, 빠르게
그린 제스처일수록 더 어긋납니다.

녹음에는 그 동작이 얼마나 걸렸는지가 이미 들어 있습니다 — 뒤따르는 지연입니다. 그래서
`KeyEngine::runMoves`가 다음 레코드를 미리 보고, `ACT_DELAY`면 그 시간에 걸쳐 이동을
잘게 나눠 내보내고 그 지연을 소비합니다. 그러면 재생 속도가 녹음 속도와 같아지고,
가속 곡선이 손에 걸렸던 것과 똑같이 재생에도 걸려 **상쇄**됩니다.

- 127을 넘어 레코드 여러 개로 쪼개진 조각은 뒤따르는 지연을 **나눠 씁니다.** 각자 다
  가지면 쪼갰다는 이유만으로 제스처가 길어집니다.
- 뒤에 지연이 없는 마지막 이동도 조각이므로 `MK_MACRO_MOVE_SLICE_MS`(50 ms, 호스트의
  `MOTION_SLICE_SECONDS`와 같은 값이며 펌웨어 합의 테스트가 붙들고 있습니다)를 씁니다.
- 사람이 멈춰 있던 긴 지연까지 이동에 쓰면 포인터가 기어가므로
  `MK_MACRO_MOVE_SPREAD_MAX_MS`(150 ms)에서 자릅니다. 나머지는 그냥 지연입니다.
- 레코드를 **추가로 쓰지 않습니다.** 지연을 소비할 뿐입니다.

포인터 가속을 `flat`으로 두면 변수 자체가 사라져 재생이 정확해집니다. 설정 앱이 마우스
녹음을 켤 때 이를 감지해 **묻고**, 승낙할 때만 바꿉니다. 남의 데스크톱 설정이라 조용히
바꾸지 않습니다.

## 8. 호스트 앱 구조

```
macrokey/
├── boards.py    지원 보드 레지스트리 — 아래 전부가 여기서 파생됨
├── config/      profile 모델 · 저장소 · 스키마 마이그레이션 · 보드별 레이아웃
├── device/      시리얼 transport · 프로토콜 코덱 · 포트 탐색 · 자동 재연결
├── flash/       보드 인식 → 부트로더 진입 → 펌웨어 쓰기
│   ├── attached.py  무엇이 꽂혀 있고 어떤 상태인가
│   ├── images.py    번들된 펌웨어 이미지 찾기
│   ├── uf2.py       부트로더가 USB 드라이브인 보드 (파일 복사)
│   ├── avr109.py    부트로더가 시리얼인 보드 (avrdude 없이 직접)
│   └── service.py   위를 엮는 순서
├── session.py   홀드 녹음 상태머신
├── capture_setup.py  Wayland input 권한 첫 실행 설정
├── recorder/    입력 캡처 · 정규화 · 장치 매크로 컴파일
└── ui/          PySide6 화면 (얇게 유지, 교체 가능)
```

`flash/`가 외부 도구를 부르지 않는 것은 의도입니다. 플래싱이 필요한 상황은 대개 패드가
말을 안 하는 상황이고, 그때 arduino-cli나 avrdude를 설치하라고 하는 것은 답이 아닙니다.
UF2 보드는 파일 복사, AVR109 보드는 pyserial 위의 작은 프로토콜이라 둘 다 네이티브
의존성이 없습니다.

핵심 규칙은 **`ui/`를 제외한 어느 계층도 UI 툴킷을 import 하지 않는다**입니다.
헤드리스 CLI·테스트는 이 규칙 덕분에 됩니다.

PySide6 · pyserial · pynput · evdev는 **배포 번들(PyInstaller)** 에 포함됩니다.
개발은 `pip install -r requirements.txt` / `python main.py`.

장치 통신(connect · push · pull)은 워커 스레드에서 돌고, GUI는 Qt 시그널로 갱신합니다.

## 9. 확장 지점 정리

| 늘리고 싶은 것 | 건드릴 곳 |
| --- | --- |
| 새 장치 액션 | `ActionTypes.h` + `KeyEngine` dispatch |
| 새 LED 효과 | `LedEffects` 함수 + 테이블 |
| 키/LED 개수 | `Config.h`와 호스트 `KEY_COUNT`/`LED_COUNT`를 같이. 키가 8개를 넘으면 `mk_keymask_t`도 함께 넓혀야 하고, 안 넓히면 `Config.h`의 `static_assert`가 빌드를 세웁니다 |
| 다른 보드 | `macrokey/boards.py`에 `Board` 하나, `firmware/src/boards/`에 헤더 하나, `docs/boards/`에 문서 하나. 그 외에는 아무것도 — 자세한 절차와 검사 항목은 [BOARDS.md](BOARDS.md) |

## 10. 의도적으로 하지 않은 것

- **키 매트릭스 스캔** — 8개는 GPIO 직결로 충분합니다.
- **PC에서 셸·클립보드 실행** — 패드는 HID만. 앱은 상시 런타임이 아닙니다.
- **자동 양방향 동기화** — 충돌 시 Pull/Push/Cancel. Cancel은 명시적인 diverged 상태로 남아
  이후 편집이 어느 한쪽을 몰래 덮어쓰지 않습니다.
- **암호화된 시리얼** — 로컬 USB + HID.

## 11. 안전 고려

- 부팅 직후 2초 HID 억제.
- `SEQUENCE` 최대 레코드·실행 시간 상한.
- 녹음 중 LED 빨강/분홍 pulse.
- 비밀번호로 보이는 캡처 구간 제거 시도.
